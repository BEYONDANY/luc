## 3. 方案对比（在默认假设下）

在董事会回答前，采用以下**临时默认假设**以便评审方向（可被 Q1–Q6 推翻）：

- 多端统一账号（Web + App）
- 首期：短信登录 + 密码登录；预留 OAuth
- 单产品单租户起步，数据模型预留 `tenant_id`
- 用户中心首期：资料 + 安全设置 + 会话管理；RBAC 仅基础角色

| 方案 | 要点 | 优点 | 风险 / 代价 | 适用 |
|------|------|------|-------------|------|
| **A. 自建 Auth + User Service（推荐）** | 独立 `auth-service` + `user-service`，对外 OIDC/OAuth2 兼容；BFF 给各端发会话 | 可控、可演进、不绑死厂商 | 安全与合规自担；首期工程量中等 | 中长期核心账号资产 |
| **B. 托管 IdP（Auth0 / Cognito / 国内等价）+ 薄用户资料服务** | 认证交给托管；业务资料自建 | 上市快、安全基线高 | 成本与厂商锁定；定制 SSO/风控受限 | 验证产品、人力紧 |
| **C. 单体模块先行** | 同一应用内 `auth`/`user` 模块，后期再拆 | 空仓库启动最快 | 边界易糊；多端扩展时重构成本高 | 极小团队 MVP |

**推荐：方案 A（可先以模块化单体仓库落地，进程内清晰边界，接口按服务边界设计，便于后续拆分）。**

## 4. 推荐架构（方案 A 细化）

### 4.1 逻辑架构

```text
[Web/App/BFF] --HTTPS--> [API Gateway / BFF]
                              |
              +---------------+---------------+
              |                               |
        [auth-service]                  [user-service]
         - 登录/注册/验证码                   - 资料/绑定
         - Token 签发/刷新                    - 偏好设置
         - 会话/设备                          - 注销与角色（基础）
              |                               |
              +--------[PostgreSQL]-----------+
              +--------[Redis: session/OTP]---+
```

### 4.2 关键能力切片

1. **身份认证**：短信 OTP、密码哈希（Argon2id）、刷新令牌旋转、登出作废。
2. **会话**：短时 access token（JWT 或不透明 token）+ 可撤销 refresh；设备维度会话列表。
3. **用户资料**：最小字段集（id、手机号、昵称、头像、状态）；变更审计。
4. **安全**：OTP 频控、登录锁定、风控钩子（可先日志后策略）。
5. **集成面**：对内提供 `GET /me`、JWKS（若 JWT）、服务间 m2m client credentials（二期）。

### 4.3 建议技术栈（无偏好时的默认）

| 层 | 建议 | 理由 |
|----|------|------|
| API | TypeScript + NestJS 或 Fastify | 类型安全、生态成熟、易拆服务 |
| DB | PostgreSQL | 账号/权限关系清晰 |
| Cache | Redis | OTP、会话、限流 |
| 前端用户中心 | 独立轻量 Web（或嵌入主站） | 与业务前端解耦 |
| 可观测 | OpenTelemetry + 结构化日志 | 安全审计与排障 |

> 若董事会有既定 Java/Go/PHP 栈，保持边界不变，仅替换实现语言。

### 4.4 仓库与交付节奏（确认后的实现拆分预览）
